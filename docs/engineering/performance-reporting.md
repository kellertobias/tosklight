# Published performance measurements

The Development page is generated by `tools/performance-publication.mjs` from
`status.json`, produced by `tools/run-release-performance.mjs`. The documentation
workflow measures downloaded release binaries, not a debug build. The report records
the binary release commit and the measurement-tooling commit separately. Reporting
fixes can therefore remeasure an existing release without relabelling its binaries.

## Separate measurement paths

- **Control baseline:** the released Tauri Desk and its actual Fixture Sheet, with
  Dynamics active, requesting 40 output ticks per second. Stage is explicitly off;
  the harness verifies the mode acknowledgement and renderer absence. The exact portable demo is copied into the isolated startup-show path before
  Tauri starts, avoiding an overlapping show switch during frontend bootstrap. The demo
  also runs with the complete application tree restricted to one CPU core.
- **Engine-only probe:** the released `light-benchmark` executable, without Tauri,
  WebKit or Stage. Its fixture workload and requested cadence are recorded separately.
  Its throughput does not certify complete desk or visualizer performance.
- **Stage acceptance:** use the packaged GPU scenarios in
  [Stage performance](../testing/16-stage-performance.md). Software rendering on a
  shared GitHub runner is not a replacement for those scenarios.

The small Control case has four Robin LEDBeam 150s, four ten-cell Sunstrip RGBs,
and sixteen dimmers: 24 fixture records and 224 patched DMX slots in one universe.
The shipped profiles yield 188 animated target/component addresses in 20 Dynamics.

## Counts and rates

A DMX-slot count measures occupied patched universe/address pairs, including fine
bytes and physical multipatches. An unpatched fixture remains programmable but
contributes no patched output slots. Dynamic attributes count animated components on
fixture/logical-head targets, including virtual intensity. These are different units.
Missing profile metadata must fail a new measurement instead of silently counting zero.

Output cadence counts completed scheduler ticks, not datagrams, universes or display
frames. Extra action-triggered wakeups can exceed the configured periodic rate.
The slow-tail headline is the fifth percentile of sampled-window rates: approximately
95% of windows held that rate or better. It is not the conventional 95th percentile
of rate values. Mean cadence is total completed ticks divided by elapsed server time.
Request timestamps remain diagnostic evidence; the output counter and its same-lock
server monotonic timestamp determine rates. Actual elapsed duration is reported.

Patched universes and configured output routes are separate quantities. Each new
case disables inherited routes and enables one 512-slot Art-Net unicast route per
patched universe, targeting an owned localhost receiver. Bounded received-packet
counts verify transport work without retaining DMX payloads. A localhost receipt
is not proof that external hardware observed those universes.
CPU percentages use one logical core as 100%; a four-core process tree can use 400%.

## October 2026 legacy report audit

The public 2.6.3 report was generated on 22 October 2026 by Documentation run
39715734631, performance job 119617337210, on an AMD EPYC runner with four logical
CPUs and about 16 GiB RAM. It must not be presented as a 1.0.0 measurement.

That report had four relevant defects/limitations:

- Demo slots read an obsolete inline profile field and became zero. Dynamics joined
  normalized profile revisions correctly, so the reported 1,575 animated attributes
  were real. Mixed shows masked the counter bug with a separately generated count.
- The fixture-sheet harness also enabled native Stage under software graphics.
  The unrestricted demo renderer alone averaged 189% CPU. Its aggregate CPU and
  output rate are not a renderer-off Control baseline.
- Sixty polling iterations took 63–77 seconds. HTTP midpoint estimates exaggerated
  some slow/fast interval extremes; overall means still confirmed real shortfalls.
- The table's 30.8 Hz was the one-core demo's slow tail, versus its 37.7 Hz mean and
  40 Hz target. The nearby 99.3 was CPU percent. The separate engine probe averaged
  59.93 Hz against 60 Hz. Historical 100 Hz probes are another measurement again.

Those observations demonstrate substantial extra workload and measurement defects;
they do not isolate one engine bottleneck. A matched Stage-off rerun is needed before
attributing the remaining throughput difference to any particular engine phase.
