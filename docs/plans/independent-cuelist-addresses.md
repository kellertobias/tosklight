# Independent Cuelist addresses

Cuelist numbers identify portable Cuelist objects. Playback numbers identify physical Playback definitions. Cuelist 101 may coexist with a Speed Group assigned to Playback 101. Recording the first Cue in an empty Cuelist creates and selects the Cuelist without creating a Playback definition or page assignment.

The additive portable fields are `pool_number` and `legacy_pool_aliases`. Existing files without these fields retain their numeric meaning: each legacy Playback definition targeting a Cuelist supplies an address, the lowest becomes canonical, and the remaining numbers become explicit aliases. Different Cuelist identities claiming one address are rejected with an actionable error. Duplicate assignments to the same identity remain valid. An orphan Cuelist receives the lowest free address after all meaningful legacy addresses have been reserved, in stable UUID order.

Only a truly absent legacy topology, with neither Playback definitions nor pages, reproduces the historic input-order default assignments. An intentionally stored empty page is not absent topology. Migration preserves Cuelist UUIDs, Cue UUIDs, existing programming and live Preset references, unknown JSON fields, physical assignments and page contents. Once explicit metadata exists, moving a physical assignment cannot rebind a Cuelist number.

The first independent-numbering mutation authors the metadata for existing Cuelists and its target in one portable transaction. Such payload requires programming feature contract 3; supported readers accept contracts 1, 2 and 3. Older readers that support only 2 reject these files instead of silently using Playback numbers. Literal contract-1 and referenced contract-2 files retain their existing marker until independent-numbering data is authored. Writers never downgrade an existing higher marker. Dynamic `pool_number` fields do not invoke this gate.

Persisted candidates containing both explicit and legacy Cuelist addressing are rejected before commit. During the brief UI response/event reconciliation interval, legacy lists retain their assignment-derived addresses; an explicit address colliding with another list's legacy alias is rejected rather than relabeled. Recording Undo restores the historical cue contents and unknown fields while preserving the completed namespace migration if that historical body predates independent numbering. Explicit historical address metadata remains authoritative, including Move history. The guarded SQLite Undo writes the same migrated body prepared for runtime and retains the original current body for Redo.

Explicit Cuelist selection is a desk/show scoped UUID. A legacy selected Playback continues to supply the selected Cuelist only while no explicit Cuelist is selected. Selecting a Playback clears explicit Cuelist selection even when the Playback number itself did not change. Canonical Cuelist addresses, aliases and assignment-owned runtime state remain distinct in the UI and control adapters.

Verification must cover legacy aliases, conflicting identities, absent versus intentionally empty topology, standalone first-Cue recording with a reserved physical number, selected-Cuelist follow-up recording, armed Record through the pool tile, assignment preservation, feature rejection and save/reopen. Source checks and operator acceptance are reported separately in the release evidence folder.
